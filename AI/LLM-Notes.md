# Inference of Decoder Transformer LLMs

## GPU Structure
- Many compute units with their own fast but small SRAM. They are used to perform parallel matrix operations.
- VRAM: the main memory with much larger total capacity than each SRAM, but slower to load from.
- Memory bandwidth: speed of loading data from VRAM into SRAM of compute units.

## Prefill v.s. Decode
- Prefill and decode are different stages in the inference operations.
- Prefill: faster, process the whole prompt, which can be parallelized by the GPU matrix operations.
- Decode: slower, needs to wait for the previous token to be generated in order to generate the next.

## Decoding Strategies
- Temperature: a parameter that adjusts the final distribution of the next token in the vocabulary by dividing all logits by T before applying softmax.
    - Higher temperature flattens the distribution (smaller relative differences between logits), making the output more random.
    - Lower temperature sharpens the distribution (larger relative differences between logits), concentrating probability on top tokens and making the output more deterministic. 
- Top K and Top P
    - Top K: limit the candidate pool to the top K tokens ranked by probability
    - Top P: limit the candidate pool to group of tokens with total P probability
    - When both are applied, usually top-K is applied first, then the distribution is renormalized, and finally the top-P filter is applied. The order matters because of the renormalization in between.

## Speculative Decoding
- Instead of generating each token autoregressively, use a smaller but similar draft LLM to predict a series of upcoming tokens, then use the target (large) LLM to verify them.
- Similar to prefill, the target LLM can evaluate the entire series of candidate tokens in parallel, which is fast.
- If the draft and target LLM agrees most of the time, then it speeds up the generation process.
- Method of checking: compare the token distributions from both models. If the target LLM assigns a higher (or equal) probability to the draft's token than the draft does, the token is always accepted. Otherwise, it is accepted with a probability ratio (to maintain the correct distribution). If any token in the series is rejected, sampling continues from the target model conditioned on the accepted prefix.

## Structured Output
- Structured output is generated by combining the following techniques
    - Finetuning the LLM on "tool/function calling/usage" because tool calling requires accurate JSON format. This improves the LLM's capability to output correct JSON.
    - Use structured output (constraint decoding) engines like XGrammar or Outlines to constrain the token generation.
- Constraint decoding has 2 potential downsides: 1. more CPU overhead; 2. possibly degrades model performance.

## KV Cache
- When generating the next token, the current (last generated) token's Q, and all previous tokens' (including the current) K and V values, are needed to compute the attention.
- K and V from all previous tokens (including the current token) can be cached for later token generation, as they remain unchanged. The Q for each token is only needed for its own attention computation and is not cached.
- KV Cache takes extra VRAM besides the memory used to load the model weights.

## Quantization
- A typical full-precision BF16 LLM uses 16 bits (2 bytes) to store each model weight. So an n-billion-parameter LLM takes 2n billion bytes (approximately 2n GB) in VRAM.
- Quantization, such as GGUF, reduces the precision of each weight. For example, by storing each weight as an 8-bit float, it uses half the memory compared to 16-bit.

## FlashAttention
- Softmax computational bottleneck in attention: softmax requires all inner product finished between the Q of current token and KVs of previous tokens.
- FlashAttention: keeps the loaded partial K, V, Q in fast SRAM without writing the intermediate attention matrix back to VRAM. Instead of computing all pairwise inner products and storing them, it uses an online softmax algorithm to perform the summation/aggregation incrementally.

## Deployment
- Use a load balancer to distribute inference requests across all GPUs
- Use dynamic batching to group requests from different users into larger batches
- Use prompt caching to share the KV cache across similar requests.
